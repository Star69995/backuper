# Backuper - project notes

Personal Windows-only backup app (drive to drive, same PC). Tauri 2 + React 19 + Tailwind 4 + lucide-react; Rust core using robocopy.
UI is Hebrew, RTL, light/dark. See README.md for user-facing behavior.

## Layout

- `src-tauri/src/`
  - `model.rs` - all serialized types (camelCase JSON, mirrored in `src/types.ts` - keep both in sync).
  - `schedule.rs` - next-occurrence math (local time, DST-safe) + validation.
  - `engine/mod.rs` - `CopyEngine` trait (`mirror` for full backups) + `CopyJob`/`Filters`/`ListedFile`. `engine/robocopy.rs` implements it. `engine/native.rs` is the incremental path: `list_files` (FindFirstFileExW per folder - size, mtime, attributes without opening files; filters with robocopy's exact semantics via `RtlIsNameInExpression` on the long + 8.3 name, test `listing_matches_robocopy` compares against a real robocopy mirror - keep it passing when touching filters) and `copy_files` (std::fs::copy). Backup logic must not call robocopy directly, so the engine stays swappable.
  - `filters.rs` - user `FilterRule`s -> engine `Filters` (+ validation). `Include` values are extensions or wildcards (`patterns`). `Regex` rules (`include_regex`/`exclude_regex`, or `exclude_dir_regex` when `folders` is set - match the folder name at any depth, skip only, so `include` + `folders` is invalid) are applied by `native` directly; robocopy can't, so `native::resolve_regex` runs before a full `mirror` and rewrites them into plain file names / folder names (`Listing.regex_dirs`) (the fast-full reuse is skipped with an include rule or include regex).
  - `cobian.rs` - parses Cobian `.lst` task lists (UTF-16, `<§- guid -§>` sections linked by `{ *§* guid *§* }`) into `Task`s + per-task warnings (Cobian's `TaskGroup` -> `Task.group`; the import dialog puts only the group-less tasks into the list file's name group). `import_tasks` reads either format (Cobian or our own export) and only previews (prepare + folder-conflict check); saving goes through `save_tasks`. UI: `ImportTasksDialog.tsx` (`useTaskListTransfer` hook = import/export/restore, used by TasksView and SettingsView). A Cobian import is two steps: review, then one options page (continue from Cobian's backups now / not / decide later - only when some were found - plus switch on now/later, default disabled); other sources stay one screen. "Decide later" sets `Task.cobianPending` (imported disabled): `Core::enqueue` refuses jobs of pending tasks (scheduled, drive-connect, manual), `take_over_cobian` (when every rename worked) and `decline_cobian_takeover` clear it, and `CobianPendingDialog` (TasksView) asks when a pending task is switched on or run by hand (cancel = switched off again; tasks with no Cobian folders left are released silently).
  - `cobianmigrate.rs` - continuing from Cobian: `find_lists` (`*.lst` in `Cobian*` program folders under Program Files / ProgramData / AppData, subfolders `Lists`, `DB`, `Settings`) + `lists_dir` (where the file dialog opens), and the one-time takeover of Cobian's backup folders: `plan` reads `<source last folder name> <timestamp>[ <type>]` folders in the destination (lenient timestamp: Cobian's format is configurable) and maps them to our dated names, `apply` re-plans from disk and renames (rename only). Untyped folders: oldest = full, later = incrementals. Ambiguous names (two sources with the same last folder name in one destination), whole-drive sources and zip/7z archives are skipped with warnings. Commands `find_cobian_lists`, `plan_cobian_takeover` (works on unsaved import-preview tasks too), `take_over_cobian` (inside `Core::when_idle`). UI: `CobianDialogs.tsx`.
  - `simpleconfig.rs` - import of a plain JSON config (`{copy_sources: {src_N: [paths]}, copy_destinations: [paths]}`, e.g. `mom_config.json`): all groups merge into one manual task (fixed id `simple-config`, duplicate folders dropped, first destination). `import_tasks` tries our format, then this, then Cobian (`ImportPreview.source` = `backuper`|`simple`|`cobian`).
  - `regexcheck.rs` - live check of a regex filter for the rule editor (`check_regex` command -> `RegexCheck`): `error` (Hebrew, per `regex-syntax` error kind; also what `filters::validate` reports at save), `parts` (the AST read left to right as token + Hebrew meaning, so it is exactly what the engine parses), `note` (unanchored pattern) and a try-out against a sample name. UI: `RegexCheckPanel` in `FilterRulesEditor.tsx`; `devMock.ts` fakes it with JS `RegExp`.
  - `manifest.rs` - the `.backuper-index` file (hidden) in each completed backup folder: size + mtime (FILETIME) per file, header with count and the folder's own name, `end` line. Written after every successful backup (same walk that gives `backupBytes`), removed when a full reuses the folder. `load_or_build` = read, or walk once and write (folders from older versions). Never overwrites a non-index file of that name (it came from the source).
  - `backup.rs` - per-source chains of dated folders (`<folderName> YYYY-MM-DD HH-mm מלא|אינקרמנטלי`, `.partial` while in progress/failed/stopped; no tag = legacy full), resume (`backup_source` continues in the newest `.partial` folder of the same kind instead of creating one - full: robocopy mirror skips what's there; incremental: `skip_done` keeps matching files, deletes the rest; the folder keeps its name until it completes, then is renamed with the new date; `chain_index` ignores partial folders; `commands::resume_task` re-queues a paused task with the paused run's mode; `RunContext.fresh` (`Job.fresh`, or a Scheduled/CatchUp trigger) = don't continue a partial folder - a manual run of a `resumable` task asks continue/start over in `TasksView.run`; `Core::cancel(id, discard)`: pause = keep the `.partial` folder, stop (`useStopTask` asks keep or delete; delete = `discard`) = `discard_stopped` deletes it unless it is a reused previous full or may be one, i.e. the last complete backup; `TaskState.resumable` = last run paused and a partial folder still exists), full/incremental decision, incremental diff (native source listing vs. index of full + later incrementals from their `.backuper-index` files, by size and mtime with a 2s tolerance; unreadable source folders -> warning + FileErrors), retention (`prune` with `Keep` from `Task.keepMode`: count / days / all), delete-before, path validation. `run_task` runs all sources with one shared timestamp.
  - `core.rs` - single worker thread (one backup at a time, queue) + scheduler thread (5s tick, missed-run catch-up). Emits `snapshot-changed` and `progress` events.
  - `tasklist.rs` - the task list as a file: export format (`{app: "backuper", version, savedAt, tasks}`, a bare `tasks.json` array also parses), snapshots in `task-list-backups/` on every `Store::save_tasks` (deduped, newest 50), and the same snapshots in `<settings.taskListCopyDir>\Backuper - גיבויי רשימת משימות`. Snapshot files are read-only + hidden + system (folders hidden + system) via `SetFileAttributesW`; clear the attributes before deleting one (`remove_protected`). `Store::load_tasks` moves a damaged `tasks.json` aside, loads the newest snapshot from either place and sets `Store.notice` (shown by `NoticeDialog.tsx` until `dismiss_notice`).
  - `drives.rs` - drive-connect trigger: `task_drives` (drive roots of destination + sources), `DriveWatch::poll` fires a task when all its drives become present after one was missing (first sighting = already present, so nothing fires at startup). `core.rs` polls it on its own thread (3s) and either queues (`Task.onDriveConnect = run`) or adds to `drive_prompts` (`ask`, shown by `DrivePromptDialog.tsx`, answered via `answer_drive_prompts`).
  - `updater.rs` - self-update (tauri-plugin-updater): `Updates` (managed state, its `UpdateStatus` goes into the snapshot) checks a minute after start and every 6h per `settings.updateMode` (`auto`|`notify`|`off`), downloads, and installs only through `Core::when_idle` (queue empty, worker not busy, queue lock held so nothing starts). `auto` installs unasked only while the main window is hidden. Before installing it writes the `after-update` marker in the app data dir; the relaunched app reads it (`after_update`) to stay hidden and show an "updated" toast.
  - `commands.rs` - Tauri commands. `store.rs` - JSON persistence in app data dir. `tray.rs` - tray icon/menu.
- `src/` - React UI. `api.ts` wraps all `invoke` calls. `components/ui.tsx` has the primitives (Button, Modal, Menu, Toggle, PathText...). `components/feedback.tsx` has toasts + the confirm dialog. `components/sections.tsx` = card sections + side nav/chips + scroll spy (task editor, help page).
- `src/components/HelpView.tsx` - the in-app help page for end users (Hebrew, searchable, one section per topic). When user-facing behavior or a UI label changes, update the help text in the same pass. Its error list comes from `ERROR_KINDS` in `src/lib/fileErrors.ts`.
- `src/lib/devMock.ts` - fake backend for `npm run dev` in a plain browser (visual checks). Loaded only in dev outside Tauri. Mock times/backup folders derive from each task's schedule (`occurrences`), so screenshots stay consistent.
- `site/` - the public landing/download page (GitHub Pages, deployed by `.github/workflows/pages.yml`). Static HTML/CSS/JS, Hebrew RTL, no build step and no framework. Preview locally with `npm run site` (serves `site/` on http://localhost:8765, no dependency added). `app.js` fills the download buttons and the version list from the GitHub Releases API at runtime (installer = the `*-setup.exe` asset). When a significant product change lands (a new or removed feature, changed behavior users rely on, install/update flow, system requirements), update the page in the same pass: feature cards, screenshot tour, FAQ, and the "התקנה בלי לחץ" trust claims. Screenshots in `site/img/` come from `npm run dev`; retake them (and `og.png`) after visible UI changes. Don't claim things on the page the app doesn't do, and don't announce a feature before its release is published.

## Conventions

- robocopy progress is read from its UTF-16 `/UNILOG` file (stdout is OEM codepage and garbles Hebrew names). The list-only `/L` pass (progress totals) walks source + destination an extra time, so it is off by default (`CopyJob.totals`, chosen by `backup::totals_source`): a fresh full folder gets an estimate from the previous full's `.backuper-index` (`TotalsSource::Estimate`, percent capped at 99); a reused or resumed (`.partial`) folder shows counters only (`Unknown`); with no previous index (first backup) or `settings.exactProgress` it scans (`Scan`). Incrementals always walk the source once (native listing, exact totals).
- Never delete anything in a destination that isn't one of the task's own dated folders (`list_backups` pattern match).
- A drive root is hidden + system, and robocopy copies the source folder's attributes onto the backup folder, so a backup of a whole drive was invisible in Explorer (default settings). `backup::unhide` clears them at the first copied file and after the run; keep it when touching the full-backup flow.
- A task has a main `schedule` (its type = `mode`) and, in combined mode (`mode = incremental`), a `fullSchedule` with its own `nextFullRun` in state. Scheduler slots go through `take_due`/`refresh_slot` in core.rs. A due full wins over (and upgrades a queued) incremental.
- Tasks can be grouped: `Task.group` (free text, empty = the general list "כללי"). A group exists only through its tasks (UI keeps just-created empty groups in state); renaming/dissolving a group is a `save_tasks` of its tasks. Helpers + `GroupInput` (a `Menu` of the existing groups + "קבוצה חדשה..." that turns into a text field; `Menu` has a `fill` mode for form fields)/`GroupNameDialog` in `src/components/groups.tsx`; the shown tab is per-machine (`localStorage`).
- A task has `sources: Vec<Source{path, folderName}>` + one destination. `(destination, folderName)` must be unique across all tasks (checked in `save_tasks`). Old single-`source` tasks are migrated in `Task::migrate`.
- Run records hold per-source results (`RunRecord.sources`), each with its own log file (`logs/<runId>-<i>.log`, UTF-16).
- Per-file errors are `FileError{path, code, message}` (`code` = Win32 error, from robocopy's `ERROR n` line or `io::Error::raw_os_error`; old history strings `"path - message"` are parsed on load). The UI (`src/lib/fileErrors.ts`) groups them by code and explains each group (why + what to do) - add new codes there, never show a bare OS message alone. Run-level failure messages also end with what to do.
- Task config vs runtime state are separate (`tasks.json` vs `state.json`), so edits/undo never touch next/last run. Changing a task's schedule/enabled clears `nextRun` so it gets recomputed.
- Bulk edit, undo and import all go through `save_tasks` (all-or-nothing validation).
- Per-machine UI prefs (task sort, task table column widths, compact table view) live in `localStorage`, read/written in try/catch. Compact view (`backuper.taskCompact`, toggle next to the search box in TasksView) drops the text from the "מצב" / "סוג" columns (toggle only / kind icon) and pins both to a narrow fixed width (`COMPACT_COLS`), so the columns get more room. The task table never scrolls sideways: `TasksView` measures the table (ResizeObserver) and `fitColumns` (`lib/useColumnWidths.ts`) shrinks the wanted widths towards per-column floors (`COL_FLOORS`: wide enough for the column's non-wrapping badges/toggle label, e.g. 112 for "ריצה אחרונה") to fit; dragging a border is clamped to the floor and so the sum can't exceed the table width. When even the floors don't fit (the 820px minimum window), `NARROW_DROP` hides "סוג" then "תזמון" (the kind shows as an icon next to the task name, the schedule as a tooltip on the next-run cell), so the name and status stay readable.
- Paths in the UI: render with `PathText` (LTR, each segment bidi-isolated). Byte sizes: wrap in `<bdi dir="ltr">`.
- Autostart: `settings.startWithWindows` is the source of truth, synced to the registry on every launch (`commands::apply_autostart`); an uninstall removes the Run entry, so a one-time registration isn't enough. Debug builds never touch the registry (would register the debug exe).
- The NSIS installer uses a custom template (`src-tauri/nsis/installer.nsi`, Tauri 2.12.1's with changes marked "Backuper:"): upgrades update in place without the "already installed" page. Re-sync the template when upgrading `@tauri-apps/cli`. `src-tauri/nsis/Hebrew.nsh` translates Tauri's own installer strings (all 27 keys); save it as UTF-8 **without** BOM (Tauri adds one, two break makensis).
- Version lives in package.json, package-lock.json, tauri.conf.json (drives the installer), Cargo.toml and Cargo.lock - bump all together with `npm run bump` (`scripts/bump-version.mjs`), never by hand in one place.
- Releases: `npm run release` (`scripts/release.mjs`; notes from commit subjects since the last release unless a notes file is passed, asks before publishing, `--yes` skips that) builds signed (`createUpdaterArtifacts`), writes `latest.json` and publishes the GitHub release. The updater endpoint is `releases/latest/download/latest.json`; the private signing key lives outside the repo (`~/.tauri/backuper.key`, never commit it).
- Speed matters (big trees on HDDs): never stat/open files one by one in a scan (a per-file `fs::metadata` cost ~26s per 200k files on HDD; directory enumeration already returns size/mtime/attributes), and don't walk the destination when an index file can answer (`has_files`/`backup_size` skip or use it).
- Tests: `cargo test` includes end-to-end runs against real robocopy in temp dirs.
- Windows service mode isn't implemented yet. Keep `core.rs` UI-independent so it can move into a service.

## Web UI rules

Apply only in projects with a browser-based user interface.

- Use `-` (hyphen), never `—` (em dash), in UI copy/text.
- Minimum text size: 12px. Layout must stay usable down to a 320px viewport width.
- Focusable fields (`input`, `textarea`, `select`) need `font-size: 16px` or larger - this overrides the 12px minimum above. Below 16px, iOS Safari zooms the page in when the field gets focus, and that zoom shifts the visual viewport, so sticky/fixed bars drift off screen and the user has to pinch back out. Never solve it with `user-scalable=no` or a permanent `maximum-scale=1` in the viewport meta: Safari ignores the former anyway, and both block pinch-zoom for everyone for the whole visit. If a field genuinely must show smaller text, add `maximum-scale=1` to the viewport meta on `focusin` and remove it on `focusout`.
- **iOS Safari's on-screen keyboard shrinks and offsets the *visual* viewport without touching the *layout* viewport, and doesn't fire `visualViewport` events continuously during its own open/close animation** - any sticky/fixed bar (header, toolbar, action bar) can drift off-screen or end up hidden behind the keyboard. This does not reproduce in a desktop browser or in the iOS Simulator's software keyboard - it needs a real device to test. Extensively tested across many real-device approaches, on a page with a *stack* of several sticky bars (not just one): the fix that looks obvious - give each bar its own `transform`/`top` that chases `window.visualViewport.offsetTop` - is fragile once there's more than one bar. It breaks in different ways depending on the exact implementation: z-index ordering between the bars becomes load-bearing and easy to get backwards (a bar with no explicit `z-index` silently paints *underneath* a sibling that has one, even if it's later in the DOM), and WebKit can glitch-repaint (a bar flickers transparent/disappears) even with a permanently-applied `transform` meant to keep it on a stable GPU layer. The approach that held up cleanly, repeatedly: don't move each bar - make the **app's own outer shell** the thing that tracks the keyboard. Give the shell `position: fixed` with its `top` and `height` bound to CSS variables kept in sync with `visualViewport.offsetTop` and `visualViewport.height` (a `resize`/`scroll` listener on `window.visualViewport`, refreshed every frame via `requestAnimationFrame` for as long as a field has focus - listeners alone leave the frame visibly lagging behind the keyboard's open/close animation). With the shell's own geometry always matching what's actually visible, everything inside it - header, sticky toolbars - can use plain normal-flow/sticky positioning with no per-element `transform` or `top` hacks at all: there's nothing to chase, so there's no overlap or stacking-order question to get wrong. Separately, and just as easy to miss: scroll the newly-focused field into view **on focus**, not only once the user starts typing - a field near the bottom of scrollable content can end up hidden under the keyboard the instant it opens, before any keystroke, and no browser does this for you automatically inside a custom scroll container.
- **Don't layer a manual "scroll the caret/focused element into view" correction on top of an auto-scroll mechanism that already exists** (a rich-text editor's own built-in scrollIntoView, or the browser's native reveal-on-focus scrolling) - **two scrollers acting on the same container in the same animation frame is what produces a visible jump/overcorrection, not a missing feature.** This surfaced as: typing in the *last* line of a scrollable editor on iOS Safari made the whole view jump to the top instead of scrolling down slightly to reveal the caret - happened only there, not mid-document, because with no more room to scroll down, the browser's own reveal-scroll escalates the gesture to an ancestor/the whole page instead of the exhausted inner container, and a second corrective `scrollBy` fighting it in the same frame is what turned that into a jump rather than a no-op. Diagnosing this kind of "two scrollers fighting" bug: put a kill switch on each of your own correction mechanisms and disable them all first - if the symptom disappears completely, your code (not the platform) is the thing to fix, and you can binary-search which mechanism and which direction (scrolling up to reveal a caret hidden under sticky top bars, vs. scrolling down to reveal one hidden under the keyboard) is the culprit by re-enabling one branch at a time. The fix that held up: don't add a second scroll call after the fact - find the hook that lets you feed the *existing* mechanism what it doesn't already know (e.g. ProseMirror's `editorProps.scrollThreshold`/`scrollMargin`, which it already applies on every content transaction) so there's still only one scroller. Concretely, for an editor with sticky top bars covering part of the scroll container: set `scrollThreshold.top`/`scrollMargin.top` to the sticky stack's covered height so the editor's own scrollIntoView already treats that height as hidden, and **leave the bottom/keyboard side at its default** - the editor and the browser already handle "caret hidden under the keyboard" correctly on their own, and adding a bottom-side correction is what reintroduces the fight. If the covered height can change (a bar that's conditionally shown, a toolbar that wraps to two lines at narrow widths), make the threshold/margin a live getter, not a value computed once - re-measure the DOM on each read rather than caching a stale number.
- No emoji in UI elements - use an icon library or SVG instead.
- Never use native browser dialogs (`alert()`, `confirm()`, `prompt()`) for user-facing interaction - always build a custom in-app modal component instead. Native dialogs can't be styled to match the app, don't respect the page's language/RTL direction or button-label conventions, and (`confirm`/`prompt`) block the JS thread while open.
- Every site needs Open Graph + Twitter Card meta tags in `<head>` (`og:title`, `og:description`, `og:image`, `og:url`, `og:image:width`/`height`, `og:locale` set to the site's actual content language (e.g. `he_IL`, not the visitor's), `og:image:alt` describing what's shown in the screenshot, `twitter:card` set to `summary_large_image`), pointing at an absolute image URL. The preview image (1200x630) must be an actual screenshot of the site/app in use, taken from a running instance (dev server or deployed site) - not a designed/illustrated graphic and not a logo or title card with no real UI in it. Resize/crop the raw screenshot to fit; don't composite it into invented artwork. To get that screenshot:
  1. Start a dev server yourself and open the app in a browser tool.
  2. If the page is empty/blank by default (no seed data), fill in a few fields with realistic-looking demo content first, so the screenshot represents actual use rather than an empty form. Don't persist this anywhere real - it's only for the screenshot.
  3. Pick a state that's actually representative of the product, not just whatever the default view happens to render. If the UI varies by real-world context (time of day, date, etc.), deliberately set it to a meaningful state (e.g. override `Date` in the page via the browser tool) rather than settling for whatever the literal current moment produces.
  4. Capture the screenshot directly at (or cropped/resized to) the target dimensions (1200x630) - don't composite a differently-shaped screenshot into a designed frame.
  5. Clean up: close the browser page/tab and stop the dev server you started.

Note: this is a desktop app, not a website - the Open Graph rule doesn't apply unless a web page is added.
